# Working method (one agent = a team of one)

This is how a single agent works on a task. Every role in `roles.md` (lead, coder,
verifier, reviewer, sweeper) follows it, and a lone agent without a team follows it too.
Repo facts (commands, layer rules, coding standards, security rules) live in the repo's
`AGENTS.md`; this file says HOW to work, not WHAT the repo must satisfy. A concise copy for
the repo is generated by `agent_team.py init` as `.agents/rules/agent-workflow.md`.

Sections 2 to 7 distill ideas from public agent harnesses (karpathy-skills,
obra/superpowers, gstack, ECC, planning-with-files, caveman); treat them as inspiration,
not quotation.

## 1. Ground before you edit

1. Read `AGENTS.md`, `.agents/project-profile.json` (when present), `.agents/CODEBASE_MAP.md`
   (when present), `.agents/memory/lessons.md` (the repo's mistake ledger) and the files
   next to the code you will touch. Read targeted line ranges or symbols, not whole large
   files.
2. The task spec is the plan: `docs/tasks/TASK-<n>.md` with its `check:` lines. Do not
   keep a second plan file. If the work spans several sessions, tick the criteria in the
   spec and note progress there.
3. For non-trivial mechanics (pagination, offline sync, token refresh, queues,
   transactions) look at how the repo's anchored reference repo (`referenceRepo` in the
   profile) does it before inventing a design.
4. State assumptions or ask once when requirements have conflicting readings; never pick
   one silently. If asked for an unsafe or architecture-breaking shortcut (SQL in a view,
   disabled auth/TLS, hardcoded secrets), say so and propose the clean alternative.
5. Turn vague goals ("fix checkout", "make feed faster") into pass/fail criteria with a
   `check:` command before editing, then loop until every check is green.

## 2. Keep the change small

- Minimum code that solves the current problem. No speculative registries, factories or
  multi-provider layers for one concrete use (YAGNI).
- Touch only the files and lines the task needs. Do not reformat, reorder imports or tidy
  neighbouring code. Remove dead imports and helpers that your own change created.

## 3. Debugging method and the 3-strike stop

This is the single statement of the bugfix rule; the done gate enforces the recorded repro.

1. Reproduce first: a `## Repro` check that FAILS on current main (`verify --repro-before`).
   A bug that does not fail may be fixed already or misunderstood.
2. Find the root cause: read the full error, trace the bad value backward to where it was
   born. Compare with a working sibling module or the reference repo. Never silence a
   symptom with a blind `try/catch`, an arbitrary delay or an unsafe cast.
3. Test one hypothesis at a time.
4. Fix, and add a deterministic regression test that failed before the fix.
5. 3-strike stop: after 3 consecutive failed fix attempts, STOP coding. Revert the failed
   patches, write down what was proven false, and take the architectural assumption to a
   human. Do not stack hack 4 on hack 3. In a team run, three red verify rounds mean
   `blocked`.

## 4. Review lens (before you call it done)

Look at your own diff for production-only failures that unit tests miss. The cross-vendor
reviewer prompt (`review.py`) carries the same list.

- Concurrency: double submit, token-refresh stampede, a stale async response overwriting a
  newer one.
- Unbounded data: queries inside loops (N+1), `SELECT *` without limit or pagination,
  huge lists rendered without virtualization.
- Idempotency and partial failure: a retry after the server already committed; step 2 of a
  3-step write failing without a transaction.
- Trust boundaries: user A reaching user B's resource by changing an ID (IDOR, missing
  ownership check); unvalidated input; secrets or PII in logs.

## 5. Verify and deliver

1. Run the cheapest meaningful check first (single test), then lint/typecheck, then the
   full suite, then the repo audit when it exists. Commands come from the profile
   (`commands.test_single`, `commands.lint`, `commands.test_all`) or the task's `check:`
   lines. Never claim done while one of them fails.
2. Report tersely: what changed (grouped by layer or file), why, and the verification
   result with the real command output. Link files; do not paste large code you already
   wrote to disk. State what you could not verify. When working on a multi-task plan or
   parallel subagents, on **every turn** (including intermediate waits for `Coder`, `Reviewer`,
   or background `verify`), update `progress.md` in place and output **only** the compact
   `**Plan Progress:** Done X/N · Active Y/N · Remaining Z/N` header + `Task | Phase | Round | Active Agent / Note`
   table in chat — prose status sentences ("TASK-x passed verify, waiting for...") are strictly forbidden.
3. No filler narration ("let me read the file"). Act, then report.

## 6. Lessons protocol (rung ladder)

On **any** user correction, screenshot bug report, or non-obvious failure, encode the fix at
the **strongest deterministic rung** immediately on the first occurrence (do not default to
prose rules):

1. `type` — make invalid state unrepresentable or ban the unsafe API in types/signatures.
2. `lint` — lint rule, dependency-boundary rule, or escape-hatch check with a root-cause message.
3. `check` — regression test, ratchet check, or `verify` script command.
4. `helper` — shared helper or codemod/lever that makes the right way the easy way.
5. `prose` — `.agents/memory/lessons.md` only when judgment is genuinely required (include a concrete bad/good example).

Always record the lesson in `.agents/memory/lessons.md` with `rung: type|lint|check|helper|prose`
and why a stronger rung was not chosen (`Component [rung: ...]: Symptom -> Root cause & fix`).
If the immediate systemic fix is too large for the current task, file a follow-up task.

**No-progress + discard rule:** during verify loops, make the smallest change per round;
discard edits that do not improve the result, and stop as `blocked` if 2 consecutive rounds
make zero progress (same or fewer passing checks) instead of loosening checks.

## 7. Token economy

- Read `CODEBASE_MAP.md` and line ranges before opening large files.
- Prefer deterministic checks to LLM judgement; spend model effort on intent and design.
- Note a token budget before a batch run; limits (rounds, timeouts, parallelism) bound a
  stuck agent.

## 8. Done gate

Team runs: `agent_team.py gate TASK-n` decides (committed tree, green verify on HEAD,
approving cross-vendor review on HEAD, no high finding, bug repro recorded, repo audit
green). A lone agent applies the same list by hand before saying done.
